# 开发者文档规范

开发者文档服务于需要阅读源码、调用 crate API、调试运行时或参与贡献的读者。文档必须以仓库当前源码为准，不得根据 crate 名称或历史实现猜测行为。

## 目录结构

开发者文档统一放在 `content/developer/crates/` 下，并以 crate 名称作为目录名：

```text
content/developer/
├── _index.md
└── crates/
    ├── _index.md
    └── <crate_name>/
        ├── _index.md
        └── <topic>.md
```

每个 crate 必须有一份 `_index.md` 作为总文档，至少说明职责、稳定入口、核心类型、生命周期或并发边界、最小示例、测试位置和已知限制。复杂 crate 可以在同一目录增加专题文档，但专题文档不能替代总文档。

## 内容要求

- 首段说明 crate 解决的问题，以及它在 Silex 架构中的位置。
- API 名称、签名、特性开关、错误类型和生命周期约束必须与源码一致。
- 解释“如何调用”时同时解释“为什么这样调用”，尤其是所有权、借用、作用域、线程模型和清理语义。
- 对 `unsafe`、类型擦除、运行时注册表、指针或外部资源等边界明确说明不变量与风险。
- 示例应能映射到仓库中的真实 API；无法作为独立可编译片段时，必须标注省略内容和验证方式。
- 对会主动返回错误的操作使用 `Result` 处理，不在示例中用 `unwrap` 掩盖错误路径。
- 只记录已经验证的性能特征；没有基准数据时不要写具体延迟、吞吐或复杂度数字。

## 可执行示例

需要编译或运行验证的示例放在 `docs/examples/`。Markdown 页面通过 Zola 的 `load_data(..., format="plain")` 读取文件，再将内容包装为带语言标记的 fenced code 并交给 `markdown` 过滤器，以复用 Giallo 语法高亮。不要把原始源码直接插入 `<code>`，否则 Rust 泛型中的尖括号可能被 HTML 解析为标签。不要在页面中复制一份会独立演进的 Rust 代码；这样可以保证读者看到的代码与 CI 测试的代码相同。

crate 的集成测试可以通过 `#[path = "../../../docs/examples/..."] mod example;` 引入文档示例，并在 `#[test]` 中执行其公开的 `run` 函数。由于这些测试属于 workspace crate，日常 `cargo test --workspace` 会自动覆盖它们；CI 还应保留一个命名明确的文档示例测试步骤，方便定位失败原因。

如果代码只是展示 API 片段、缺少上下文或故意不能运行，必须使用普通 Markdown fenced code，并在文字中说明它不是 CI 编译示例。不要把带省略号、伪函数或未声明变量的片段放入 `docs/examples/`。

## 推荐写作顺序

1. 概览与适用场景。
2. 最小可运行流程。
3. 关键 API 与数据流。
4. 生命周期、清理、错误和并发边界。
5. 测试与调试方法。
6. 设计取舍和后续专题链接。

## 版本与验证

每次修改 crate 的公开 API、运行时语义或测试契约时，都要检查对应开发者文档。至少运行 `cargo fmt --all -- --check`、目标 crate 的 `cargo check`/测试和 `zola check`；涉及示例时还要运行示例对应的构建或测试。

如果源码与文档不一致，以源码和通过测试的行为为准，并在同一变更中修正文档。不要保留指向已经删除的 `docs/src/general_docs`、旧 mdBook 目录或不存在页面的链接。
